# Requirements Specification

**System:** Support Ticket Management  
**Version:** v1  
**Status:** Frozen for implementation  
**Sources:** Requirements analysis (`docs/requirements-analysis.md`) and human-approved decisions (Prompt 002)

Identifiers in this document are stable. Do not reuse an ID for a different meaning.

---

## 1. Functional requirements

| ID | Requirement |
|----|-------------|
| FR-001 | A user can create a ticket from the UI. The backend persists the ticket. |
| FR-002 | A user can list tickets. |
| FR-003 | A user can view a single ticket’s details, including its comments. |
| FR-004 | A user can update a ticket’s title, description, priority, and assignee. |
| FR-005 | A user can add a comment to a ticket. |
| FR-006 | A user can search tickets by keyword. Search matches **title** and **description**. |
| FR-007 | A user can filter tickets by status. |
| FR-008 | Search and status filter can be used together on the list. |
| FR-009 | Ticket and comment data are persisted in PostgreSQL and survive application restart. |
| FR-010 | The backend validates input and rejects invalid requests. |
| FR-011 | The UI displays meaningful error messages from backend failures (validation, not found, illegal transitions). |
| FR-012 | A user can change ticket status along **valid** state-machine transitions only. |
| FR-013 | The backend rejects **invalid** status transitions independently of the UI. |
| FR-014 | Status change is performed through a dedicated API operation (see API contract). |

## 2. Non-functional requirements

| ID | Requirement |
|----|-------------|
| NFR-001 | Backend is Java 21 and Spring Boot. |
| NFR-002 | Running application uses PostgreSQL for persistence. |
| NFR-003 | H2 may be used for automated tests where appropriate; it is not the runtime store for the running application. |
| NFR-004 | Backend is a REST API. |
| NFR-005 | Frontend is React / Next.js. |
| NFR-006 | Backend is the authority for validation and state-machine enforcement. |
| NFR-007 | No secrets (database credentials, passwords, keys) are committed to the repository. |
| NFR-008 | State-machine behaviour is covered by backend integration tests (all valid transitions and the specified invalid examples). |
| NFR-009 | The system is a single backend application plus a single frontend application. No additional services are required. |

**Architectural decisions (not original product requirements):**

| ID | Decision |
|----|----------|
| AD-NFR-001 | Datetimes in API JSON are ISO-8601 in UTC with offset or `Z`. |
| AD-NFR-002 | The frontend calls the backend over HTTP; local development may use a Next.js rewrite/proxy and/or CORS on the API. |

## 3. Business rules

| ID | Rule |
|----|------|
| BR-001 | Every new ticket is created with status `OPEN`. Clients cannot choose the initial status. |
| BR-002 | Ticket `id` is a UUID generated by the backend. |
| BR-003 | Priority is one of `LOW`, `MEDIUM`, `HIGH`. If omitted on create, priority is `MEDIUM`. |
| BR-004 | Title is required and must not be blank. Validation uses trimmed content; the **stored** title is the trimmed value. |
| BR-005 | Description is optional. |
| BR-006 | Assignee is optional and is a simple string. There is no user table. |
| BR-007 | Authentication and authorization are not applied in v1. |
| BR-008 | A ticket may have many comments. Comments are append-only in v1. |
| BR-009 | Comment `body` is required and must not be blank. Validation uses trimmed content; the **stored** body is the trimmed value. |
| BR-010 | Comment `author` is a string (no authenticated identity). |
| BR-011 | Ticket status may change only according to the v1 transition table in `spec/state-machine.md`. |
| BR-012 | Tickets are not deleted in v1. |
| BR-013 | Field updates (title, description, priority, assignee) and adding comments are allowed in any status, including `RESOLVED`, `CLOSED`, and `CANCELLED`. Status itself still follows BR-011. |

BR-013 is a freeze of an open analysis question: the approved decisions did not restrict field or comment updates by status.

## 4. Validation rules

Enforced on the **backend**. Frontend may mirror them for UX.

| ID | Rule |
|----|------|
| VAL-001 | Create: `title` present, non-null; not blank **after trim**; persist the trimmed title. |
| VAL-002 | Create/update: `description` optional; if a non-null string is supplied, persist that string **as given** (no silent trim). |
| VAL-003 | Create: `priority` if present must be `LOW`, `MEDIUM`, or `HIGH`; if omitted or null, use `MEDIUM`. |
| VAL-004 | Create/update: `assignee` optional; if a non-null string is supplied, persist it **as given** (no silent trim). |
| VAL-005 | Create: client must not control `id`, `status`, `createdAt`, `updatedAt`. If those properties are sent on **create**, they are ignored (**AD-API-007**). |
| VAL-006 | Update fields: at least one of title, description, priority, assignee may be sent; omitted fields stay unchanged. |
| VAL-007 | Update: if `title` is sent, it must not be blank after trim; persist the trimmed title. |
| VAL-008 | Update: if `priority` is sent, it must be a valid priority enum value. |
| VAL-009 | Update: `description` and `assignee` may be set to JSON `null` to clear. **AD-VAL-002:** a zero-length string `""` is stored as null (clear). Whitespace-only strings are **not** treated as empty and are stored as given. |
| VAL-010 | Status change via `PATCH /api/tickets/{id}/status`: body must include a target `status` that is a known status enum value. Unknown enum → 400. Known but illegal transition → 409. |
| VAL-011 | Comment: `body` required; not blank after trim; persist the trimmed body. |
| VAL-012 | Malformed JSON or wrong types → 400. |
| VAL-013 | Unknown ticket UUID (well-formed UUID that does not exist) → 404. |
| VAL-014 | Malformed ticket id in the path (not a UUID) → 400. |
| VAL-015 | List query: `status` if present must be a valid status; `q` if present is a string (empty `q` means no keyword constraint). |
| VAL-016 | Field-update `PATCH /api/tickets/{id}`: if the JSON object includes `status`, reject with HTTP 400 `VALIDATION_ERROR`. Do not change status. Message must state that status is changed only through `PATCH /api/tickets/{id}/status`. |
| VAL-017 | Comment `author` optional; if a non-null string is supplied, persist it **as given** (no silent trim). |

**Whitespace (normative)**

| Field | Validate | Persist |
|-------|----------|---------|
| `title` | trimmed content must be non-blank | trimmed value |
| comment `body` | trimmed content must be non-blank | trimmed value |
| `description`, `assignee`, `author` | length limits on the **supplied** string | supplied string (no trim) |

**Architectural decision — field length (storage safety, not a product feature):**

| ID | Decision |
|----|----------|
| AD-VAL-001 | Only `title` and comment `body` are trimmed. No other free-form fields are trimmed. |
| AD-VAL-003 | Title max 200 characters **after trim**; description max 10_000 as supplied; assignee max 200 as supplied; comment body max 5_000 **after trim**; comment author max 200 as supplied. Exceeding these is 400. |

## 5. Acceptance criteria

| ID | Criterion |
|----|-----------|
| AC-001 | A ticket can be created from the UI and appears in subsequent list/detail views. |
| AC-002 | Tickets can be listed. |
| AC-003 | Ticket details can be viewed, including comments. |
| AC-004 | Title, description, priority, and assignee can be updated. |
| AC-005 | Assignee can be changed or cleared. |
| AC-006 | Comments can be added and then appear on the ticket. |
| AC-007 | Keyword search returns tickets whose title or description contains the keyword. |
| AC-008 | Status filter returns only tickets with that status. |
| AC-009 | Search and status filter work together. |
| AC-010 | All five valid status transitions succeed and persist. |
| AC-011 | Invalid transitions are rejected by the backend with HTTP 409. |
| AC-012 | Data survives application restart when using PostgreSQL. |
| AC-013 | Backend validation returns HTTP 400 with the standard error JSON. |
| AC-014 | Unknown ticket id returns HTTP 404 with the standard error JSON. |
| AC-015 | UI shows meaningful messages for 400, 404, and 409. |
| AC-016 | State-machine integration tests pass. |
| AC-017 | No secrets are committed. |
